## 建議團隊採用（尚未核定）

以下例子只是文件示意，未在公司 Designer 編譯或執行。新規範只適用新增及本次修改的程式；既有模組若會因新規則擴大變更，另列任務。

| 主題 | 建議及簡短例子 |
|---|---|
| 命名 | 語意清楚並跟隨相鄰程式，例如筆數 `documentCount`、檢核程序 `ValidateRequest`；名稱皆為示意，不代表既有函式。不要改既有欄位名稱、別名或公開介面以追求一致。 |
| 宣告 | 新模組建議在 Options 使用 `Option Declare`，變數明列型別，例如 `Dim documentCount As Long`。舊模組補上可能揭露未宣告變數，需獨立評估，不批次加入。 |
| 作用域 | 能用程序區域變數就不新增全域狀態；例如計數使用區域 `Dim`，不因方便改成 `Public`。 |
| 程序分工 | 保留事件簽名；例如 Click 事件只協調既有驗證與儲存程序。單次需求不先建通用框架；拆分前讀完整呼叫路徑。 |
| 錯誤處理 | 按錯誤是否可恢復決定結束、回傳失敗或向上傳遞。例：必要資料存取失敗就停止該操作；不要一律 `Resume Next` 後繼續顯示成功。採用 `On Error GoTo` 時，正常結束路徑須與 handler 分開。 |
| 錯誤資訊 | 進入 handler 時保留 `Err`、`Erl`、`Error$`，再依已存在的錯誤路徑處理；例：先取得錯誤編號，再呼叫可能失敗的清理動作。不要假裝已存在 logger；敏感錯誤文字需遮蔽。 |
| 註解 | 解釋原因與限制，例如「核准後禁止修改金額，以保留審核依據」；不要只把 `count = count + 1` 翻成中文。 |
| Formula | 記錄公式所在元素、事件／欄位用途，保留多值、空值與回傳型態語意。例：改 Input Validation 公式前列出空值／合法值／非法值三種預期結果；不能只驗證一筆正常資料。 |
| DXL 內嵌程式 | 先定位 script／formula 所屬元素與事件，只改指定片段；例如調整按鈕事件的一段判斷，不重新序列化整份 XML。保留既有跳脫與 CDATA 表示。 |
| 共用 Script Library | 先找既有程式及使用者，再決定重用。例：調整共用驗證函式時，列出表單與 Agent 呼叫者，按依賴安排回歸；不複製出另一套相同函式。 |

## 修改回報

提供「設計元素／事件 → 原行為 → 預期新行為 → 最小 diff → 受影響呼叫者 → 已執行與未執行的驗證」。範例：某驗證公式原先接受空值，預期拒絕；須檢查空值及合法值，Designer／實機未測時明寫未測。

XML 與部署邊界遵守 [DXL 工作流程](dxl-workflow.md)；除錯需求遵守 [除錯規格](debugging.md)。
